RetroDesk 2 - SDK (Diskette 4)
==============================

Mit dem SDK schreiben Sie eigene Programme fuer RetroDesk 2 (RD2) in C
(Open Watcom), Turbo Pascal / Free Pascal (siehe \SDK\PASCAL\PASCAL.TXT)
oder Assembler. Englische Fassung: SDK_EN.TXT.

  \SDK\RD2.H         Typen, Konstanten, Nachrichten, Strukturen
  \SDK\RD2API.H      alle Funktionen des Kerns und der Module (Nummern fest)
  \SDK\RD2DRV.H      Schnittstelle fuer Treiber (Grafik, Klang, Netz)
  \SDK\RD2ORD.H      Kurzform der Funktionsnummern
  \SDK\RD2START.ASM  Startcode fuer Programme (wasm)
  \SDK\RD2MOD.ASM    Startcode fuer Module (.MOD) und Treiber (.DRV)
  \SDK\RD2.LIB       Bibliothek (Open Watcom, Modell Medium)
  \SDK\RDRC.EXE      Ressourcen-Compiler und Linker (DOS, laeuft auf dem XT)
  \SDK\BEISPIEL\     HALLO.C und HALLO.RC: Fenster, Menue, Mausklicks
  \SDK\PASCAL\       Unit RD2.PAS, Beispiele, Anleitung fuer Pascal


1. Ein Programm bauen (C, Open Watcom)
---------------------------------------

  wcc -0 -mm -os -s -zl -bt=dos -i=\SDK HALLO.C
  wasm -0 \SDK\RD2START.ASM
  wlink format dos name HALLO file RD2START,HALLO
        library \SDK\RD2.LIB,clibm.lib option nodefaultlibs
  RDRC HALLO.RC HALLO.EXE "Hallo"

-0 erzeugt 8086-Code (laeuft auf dem XT), -mm ist das Speichermodell Medium.
Ohne Ressourcen statt der .RC ein "-":  RDRC - HALLO.EXE "Hallo"

RDRC haengt den RD2-Block (Name, Typ, API-Version, Stapel) und die
Ressourcen an die EXE. Schalter:

  /T:P|M|D    Programm, Modul, Treiber (Vorgabe P)
  /S:n        Stapel in Bytes (Vorgabe 4096)
  /K:n        zusaetzlicher Speicher in KB
  /V:0xMMmm   Programmversion, /A:0xMMmm Mindestversion von RD2 (0x0100)
  /F:n        Flags
  /PAS        Pascal-Programm (siehe PASCAL.TXT)

Ein zweiter Lauf ersetzt den alten Anhang, die EXE wird nicht doppelt laenger.
Unter DOS gestartet meldet ein RD2-Programm "Dieses Programm benoetigt
RetroDesk 2." und endet.


2. Aufbau eines Programms
-------------------------

  #include "RD2.H"
  short RDAPI RdMain(HINST inst, LPCSTR cmd, WORD show)
  {
      ... RegisterClass, CreateWindow ...
      while (GetMessage(&m)) DispatchMessage(&m);
      return 0;                     /* Exitcode */
  }

Fensterfunktionen sind  DWORD RDCALLBACK proc(HWND, WORD msg, WORD p1, DWORD p2).
Was sie nicht selbst behandeln, geben sie an DefWindowProc weiter.
Wichtige Nachrichten: M_CREATE, M_PAINT (BeginPaint/EndPaint), M_KEY (p1 =
Taste K_*), M_BUTTONDOWN, M_COMMAND (Menue, Knopf: p1 = id), M_TIMER,
M_CLOSE, M_DESTROY (dann PostQuit).


3. Regeln
---------

- Alle Funktionen sind far pascal, alle Zeiger FAR. Handles sind 16 Bit,
  0 heisst "kein" oder Fehler. Den Grund liefert LastError() (RD_ERR_*).
- Texte sind Codepage 437 und mit 0 abgeschlossen; Laenge -1 = bis zur 0.
- Kein direkter DOS- oder BIOS-Aufruf, keine eigenen Interrupt-Handler.
  Dateien: FileOpen, FileRead, FileWrite ...; Bildschirm: GetDC, TextOut ...
- Aus der C-Bibliothek erlaubt: string.h, ctype.h, math.h, stdlib.h ohne
  system/exit, sprintf. malloc und free gehen ueber RD2.LIB auf MemFixed.
  Nicht erlaubt: printf, getch, fopen, Grafik- und Interrupt-Funktionen.
- RD2 schaltet zwischen Programmen um, wenn sie in ihrem eigenen Code sind.
  Eingaben bekommt ein Programm aber erst im naechsten GetMessage/PeekMessage.
  Lange Arbeiten deshalb in Stuecken (M_TIMER) oder mit PeekMessage zwischendurch.
- Speicher ist knapp (Rechner mit hoechstens 640 KB). Grosse Daten mit MemAlloc (verschiebbar,
  MemLock vor dem Zugriff, MemUnlock danach).
- Debug-Ausgaben mit DbgPrint/DbgHex (COM1 oder RD2DBG.TXT).


3a. Speicherfehler und Auslagerung (API 2.1)
-------------------------------------------
MemAlloc und MemRealloc liefern 0 bei Fehlern, MemLock einen Nullzeiger.
Das kann auch bei einem gueltigen Handle passieren: dessen Daten sind
moeglicherweise ausgelagert und koennen gerade nicht eingelesen werden.
Nie ungeprueft dereferenzieren. Ein FAR-Zeiger gilt nur bis MemUnlock;
keine gesperrten Zeiger ueber TaskYield, Nachrichten oder Wartezeiten halten.

LastError bleibt bei Speichermangel RD_ERR_NOMEM (bisherige Apps bleiben
kompatibel). MemError() liefert nach MemAlloc, MemLock, MemRealloc oder
MemFixed den Zusatzgrund fuer den aufrufenden Task:
  MEMERR_NONE       letzter Zugriff erfolgreich / kein Speicherfehler
  MEMERR_RAM        kein geeigneter RAM-Bereich oder Handle verfuegbar
  MEMERR_SWAPLIMIT  eingestelltes Dateilimit erreicht
  MEMERR_RESERVE    Laufwerk voll oder Freiplatzreserve unterschritten
  MEMERR_DISK       Lesen, Schreiben oder Freiplatzabfrage fehlgeschlagen
  MEMERR_SLOTS      alle 32 Auslagerplaetze belegt
Bei ungueltigen Handles gilt weiterhin RD_ERR_HANDLE, bei verworfenen
Daten RD_ERR_NOTFOUND. LastError und MemError sofort sichern, bevor weitere
Speicheroperationen den Zusatzgrund ersetzen. MemFree/MemUnlock allein
setzen ihn nicht zurueck. Erfolgreiche Allokationen/Zugriffe setzen ihn
auf MEMERR_NONE. Die Abfrage ist je Task getrennt.

Bei Fehlern eine einzelne Aktion abbrechen, eigene kurzlebige Puffer
freigeben und bestehende Dokumente/Handles behalten. MemRealloc-Ergebnis
erst in eine zweite Variable schreiben: bei 0 bleibt das alte Handle
verwendbar. Keine Endlosschleifen beim Wiederholen, kein malloc im
Fehlerpfad. Auch ein Meldungsdialog kann mangels Speicher ausfallen;
optional DbgHex protokollieren. Das SDK kann einen ungeprueften Nullzeiger
nicht automatisch sicher machen. Beispiel: sdk/SWAPSAFE.C (C, -0 -mm).
MemError ist neu an API-Nummer 0x042. Neue SDK-Programme mit dieser Abfrage
brauchen Kern 2.1; alte Funktionsnummern und Signaturen bleiben erhalten.
Die erzeugte Pascal-Unit bietet dieselbe Abfrage und Konstanten.

Optionen > System: Swap ein/aus, Dateigrenze in KB ("ohne Limit" = 0),
Freiplatzreserve in KB (0 = keine Reserve). Aenderungen gelten ab dem
naechsten Start von RD2, vorhandene Swapbloecke bleiben bis dahin lesbar.
[System] Auslagern=1, SwapMaxKB=0, SwapReserveKB=64 sind die Vorgaben.
Ein KB sind 1024 Bytes. GUI-Vorgaben reichen bis 16384 KB; vorhandene
INI-Werte von 0 bis 32767 KB bleiben beim Oeffnen erhalten. XMS hat Vorrang;
Dateilimit und Reserve gelten nur fuer die Datei, nicht fuer den XMS-Pfad.
Freie Dateibereiche koennen auch unterhalb der Reserve wiederverwendet
werden; nur Wachstum mit zusaetzlichem Clusterbedarf wird abgewiesen.


MemStats(MEMSTATS FAR *info), API 2.1 Nummer 0x043: aktueller Schnappschuss,
Rueckgabe 0. NULL -> RD_ERR_HANDLE, Auslagerung beschaeftigt -> RD_ERR_BUSY.
LastError/MemError bleiben bei Erfolg erhalten. Keine Speicherallokation.
ram_total/ram_free: Bytes der RD2-Arena einschliesslich UMB, ohne DOS/Kern
 ausserhalb dieser Arena. Belegt = total - free. Kein INI-Cache-Flush.
swap_used: gueltige ausgelagerte Nutzbytes aus Datei und XMS zusammen.
swap_file: geschriebene Dateilaenge samt Luecken, bleibt beim Einlagern und
Freigeben bestehen; auch kurze Schreibzugriffe werden mitgezaehlt.
swap_cached: momentan ungenutzte Bytebereiche in dieser Datei, als Puffer
wiederverwendbar. Keine gueltigen gecachten Kopien; belegte Dateiplaetze
zaehlen mit ihrer ganzen Laenge, also keine Anrechnung ihrer inneren Reste.
swap_free: Puffer plus moegliches Dateiwachstum nach aktivem Limit und
Freiplatzreserve, plus freies XMS. Fuer die Berechnung wird DOS 36h befragt;
auf A:/B: kein Dateiwachstum. Es werden nur ganze zusaetzliche Cluster
angerechnet, Restplatz im letzten Cluster konservativ weggelassen. Volumen
mit unbekannten Clusterparametern erhalten keinen Zuwachs. Bei 32 belegten
Auslagerungsplaetzen wird 0 gemeldet. Fragmentierung, Blockgroessen und
E/A-Fehler koennen trotzdem Allokationen verhindern: immer Fehler pruefen.
swap_maxkb/swap_reservekb: aktive Startwerte in KiB, max=0 ohne Limit.
flags & MS_SWAP: RDAUSL geladen; sonst alle Swapfelder 0. Neue INI-Werte
gelten ab Neustart. Taskmanager aktualisiert jede Sekunde und zeigt nach
RAM nur: Swap aktuell, Puffer, frei. Frei umfasst den Puffer bereits.
Belegung/Puffer werden aufgerundet, freie Kapazitaet auf volle KiB abgerundet.
Die Programmzeilen zeigen weiterhin den Ladeblock als Bild/image.


4. Ressourcen (.RC)
-------------------

Quelltext in Codepage 437, ";" leitet Kommentare ein, Texte in "..." mit
\t \n \" \\.

  SPRACHE DE|EN|ALLE        gilt fuer die folgenden Ressourcen
  TEXTE  id "Text" ... ENDE  (StrGet(inst, id), Sprache nach RD2.INI)
  MENU n
    POPUP "&Datei"
      ITEM "&Oeffnen..." 101 [GRAU] [HAKEN]
      TRENNER
    ENDE
  ENDE
  DIALOG n "Titel" x y b h [Stil...]
    KLASSE ["Text"] id x y b h [Stil...]
  ENDE
  ACCEL n   Taste Umschalt id ... ENDE
  SYMBOL|BITMAP|CURSOR|SCHRIFT|DATEN n "datei"

Klassen im Dialog: BUTTON CHECK RADIO STATIC EDIT TEXT LIST COMBO SCROLL
PROGRESS GROUP. Stile: Namen aus RD2.H (WS_*, ES_*), STANDARD = Standardknopf,
AN = angehakt, GRAU = gesperrt. Dialoge startet DialogRun(inst, n, owner,
proc, param); MenuSet(fenster, MenuLoad(inst, n)) setzt ein Menue.


5. Samples nachfuellen (Ringpuffer)
-----------------------------------

SndSamplePlay(fenster, block, rate, SM_LOOP | SM_HALBE) spielt den Block
endlos und meldet jede fertig gespielte Haelfte als M_SOUNDDONE mit p1 = 3
und p2 = 0 (erste Haelfte) oder 1 (zweite). Diese Haelfte ist dann frei und
kann mit neuen Daten gefuellt werden, waehrend die andere klingt. Ohne
SM_LOOP endet der Block wie bisher mit M_SOUNDDONE p1 = 2. Die Meldung kommt
aus der Nachrichtenschleife, nicht aus dem Interrupt. Jede Haelfte sollte
mindestens 1/10 s lang sein (bei 11025 Hz rund 2 KB), damit Zeit zum
Nachfuellen bleibt. Auf dem Sound Blaster entsteht an der Blockmitte eine
winzige Luecke, weil der Treiber jedes Stueck neu startet.
